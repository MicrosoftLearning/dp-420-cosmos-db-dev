TEST LAB....

In this exercise, you use both halves of the toolset against one Azure Cosmos DB account. You connect an AI assistant to the CosmicWorks catalog through a Model Context Protocol (MCP) server, give a shopping assistant durable memory with the Agent Memory Toolkit, and then inspect what each tool created so the boundary between them is concrete rather than theoretical.

The two halves do different jobs. The MCP server helps *you* understand data you didn't model. The memory toolkit gives your *application* a capability it didn't have. Doing both in one sitting makes the difference hard to miss.

## Before you start

To complete this exercise, you need an [Azure subscription](https://azure.microsoft.com/free/) with permission to create resources and assign roles.

If your lab environment isn't set up yet, follow [Set up your lab environment](https://github.com/MicrosoftLearning/dp-420-cosmos-db-dev/blob/main/Allfiles/Labs/Shared/00-setup-local-environment.md) to install Visual Studio Code, Git, the Azure CLI, and PowerShell 7.

You also need [Python](https://www.python.org/downloads/) 3.12 or 3.13 installed.

This exercise also requires:

- A Microsoft Foundry project with a chat model deployment and a text embedding model deployment.
- [Node.js](https://nodejs.org) 22 or later, which supplies the `npx` command the MCP server runs under.
- Visual Studio Code with the [GitHub Copilot](https://marketplace.visualstudio.com/items?itemName=GitHub.copilot) extension.

## Task 1: Set up the project and confirm the catalog

The setup script grants **Cosmos DB Built-in Data Contributor**, which allows writes. The MCP server you configure next only reads, so in a production deployment it would take **Cosmos DB Built-in Data Reader** instead.

Create a project folder and set up a virtual environment:

```bash
mkdir ai-tools-lab
cd ai-tools-lab
python -m venv .venv
```

Activate the environment. On Windows:

```powershell
.venv\Scripts\activate
```

On macOS or Linux:

```bash
source .venv/bin/activate
```

Install the packages:

```bash
pip install azure-cosmos azure-identity
```

Confirm the catalog loaded. In the **ai-tools-lab** folder, alongside the **.venv** folder rather than inside it, save the following code as `check_catalog.py`, replacing the endpoint:

```python
from azure.cosmos import CosmosClient
from azure.identity import DefaultAzureCredential

ENDPOINT = "<cosmos-endpoint>"

client = CosmosClient(ENDPOINT, credential=DefaultAzureCredential())
container = client.get_database_client("cosmicworks").get_container_client("product")

count = list(container.query_items(query="SELECT VALUE COUNT(1) FROM c"))[0]

print(f"Catalog holds {count} products")
```

Run it:

```bash
python check_catalog.py
```

The output reports 295 products.

## Task 2: Connect an AI assistant with the Azure MCP Server

Create a `.vscode` folder in the project, and add a file named `mcp.json`:

```json
{
  "servers": {
    "Azure MCP Server": {
      "command": "npx",
      "args": ["-y", "@azure/mcp@latest", "server", "start"]
    }
  }
}
```

Open the folder in Visual Studio Code, open GitHub Copilot, and switch to **Agent** mode. Refresh the tools list and confirm the Azure MCP Server appears. The server authenticates with the credentials your `az login` already established, so nothing else needs configuring.

Now work the catalog through the assistant. Start with the question you'd otherwise answer by opening documents by hand:

```text
Infer the schema of the product container in the cosmicworks database
for my Azure Cosmos DB account.
```

The assistant reports the top-level properties and how many sampled documents carried each one. Compare those properties against the shape you know from earlier in this learning path: `id`, `categoryId`, `categoryName`, `sku`, `name`, `description`, `price`, and `tags`.

Ask for recent writes, which is how you'd confirm a load succeeded without writing a query:

```text
Show me the 5 most recently modified items in the product container.
```

Then ask a real question about the data:

```text
Query the product container for items where categoryId is
3E4CEACD-D007-46EB-82D7-31F6141752B2, and return only name and price.
```

Approve each tool call when prompted. Notice what the assistant reports back: the tool it chose, and the results it got.

> [!NOTE]
> The server also carries text search and vector similarity search. Neither is exercised here, because text search needs a full-text index on the target property and vector search needs both a vector index and an embedding deployment. The `product` container has neither. That constraint belongs to the tools, not to your prompt: they operate on the indexing policy you configured.

Before moving on, note what didn't happen. You asked the assistant about your data several times and it never offered to change it. Every Azure Cosmos DB tool in the server is read-only.

## Task 3: Add durable memory with the Agent Memory Toolkit

The assistant helped you understand the catalog. It did nothing for the application, which still forgets a shopper between messages.

Your identity also needs data-plane access to the Foundry deployment, which the Cosmos DB role from Task 1 doesn't cover. Owning the subscription isn't enough, because Azure's Owner role carries no data actions and so doesn't authorize inference calls made with Microsoft Entra ID:

```azurecli
$foundryResourceGroup = "<foundry-resource-group>"

$principalId = az ad signed-in-user show --query id --output tsv

$foundryResourceId = az cognitiveservices account show `
    --name "<foundry-resource-name>" `
    --resource-group $foundryResourceGroup `
    --query id `
    --output tsv

az role assignment create `
    --assignee $principalId `
    --role "53ca6127-db72-4b80-b1b0-d745d6d5456d" `
    --scope $foundryResourceId
```

That definition ID is the **Foundry User** role. Use the ID rather than the display name, because these role names are being renamed. If you created the project yourself in the Foundry portal, you might already hold it; running the command again is harmless.

Install the memory toolkit:

```bash
pip install azure-cosmos-agent-memory==0.3.0b2
```

> [!IMPORTANT]
> Pin the version. This package is in preview, its public surface is still changing between releases, and the toolkit's own guidance is to pin when integrating.

### Provision the memory containers

Microsoft Entra ID doesn't authorize database or container creation through the Cosmos DB data-plane SDK. Assigning a control-plane role doesn't make those SDK creation calls work. Before running the memory client, use the Azure portal to provision the memory store in your existing lab account. Your identity needs a control-plane role that permits database and container creation, in addition to the data-plane role from setup.

In the account's **Features** pane, enable [vector search](/azure/cosmos-db/vector-search#enable-the-vector-indexing-and-search-feature) and confirm enrollment for [full-text search](/azure/cosmos-db/gen-ai/full-text-search). Wait for enrollment to complete before creating containers with these policies. This step doesn't add indexes to the existing `product` container.

In **Data Explorer**, use **New Container** to create the `ai_memory` database and the following containers. For each container, select dedicated autoscale throughput with a maximum of 1,000 RU/s. Use **Add hierarchical partition key** to add the second key level where the table specifies one. The [hierarchical partition key guide](/azure/cosmos-db/hierarchical-partition-keys#create-a-container-by-using-hierarchical-partition-keys) describes this creation flow.

| Container | Partition key paths, in order | Default time to live |
| :--- | :--- | :--- |
| `memories` | `/user_id`, `/thread_id` | On, with no default expiry (`-1`) |
| `memories_turns` | `/user_id`, `/thread_id` | 2,592,000 seconds (30 days) |
| `memories_summaries` | `/user_id`, `/thread_id` | On, with no default expiry (`-1`) |
| `counter` | `/user_id`, `/thread_id` | Off |
| `leases` | `/id` | Off |

For the three memory data containers, configure the following vector embedding policy. The 1,536 dimensions match the toolkit's default. Use a deployment of `text-embedding-3-large` or `text-embedding-3-small`, both of which support this dimension setting.

```json
{
    "vectorEmbeddings": [
        {
            "path": "/embedding",
            "dataType": "float32",
            "distanceFunction": "cosine",
            "dimensions": 1536
        }
    ]
}
```

Use this full-text policy for those same three containers:

```json
{
    "defaultLanguage": "en-US",
    "fullTextPaths": [
        { "path": "/content", "language": "en-US" }
    ]
}
```

Configure their indexing policy with the vector and full-text indexes:

```json
{
    "indexingMode": "consistent",
    "automatic": true,
    "includedPaths": [
        { "path": "/*" }
    ],
    "excludedPaths": [
        { "path": "/source_memory_ids/*" },
        { "path": "/supersedes_ids/*" },
        { "path": "/\"_etag\"/?" }
    ],
    "vectorIndexes": [
        { "path": "/embedding", "type": "quantizedFlat" }
    ],
    "fullTextIndexes": [
        { "path": "/content" }
    ]
}
```

For `memories_summaries`, also add the following `compositeIndexes` property to that indexing policy. Keep the preceding vector and full-text settings when you add it.

```json
{
    "compositeIndexes": [
        [
            { "path": "/user_id", "order": "ascending" },
            { "path": "/thread_id", "order": "ascending" },
            { "path": "/version", "order": "descending" }
        ]
    ]
}
```

Keep the default indexing policy for `counter` and `leases`. If the memory containers already exist, verify their keys, policies, and retention settings before continuing. Don't overwrite existing policies or delete shared data to repeat the exercise.

### Write and retrieve memory

Collect the Foundry values you need, then save the following code as `shopper_memory.py`. For the endpoint, use either the account-level inference endpoint (`https://<resource>.openai.azure.com/`) or the project endpoint the Foundry portal shows (`https://<resource>.services.ai.azure.com/api/projects/<project>`); the toolkit accepts both.

```python
from azure.cosmos.agent_memory import CosmosMemoryClient

memory = CosmosMemoryClient(
    cosmos_database="ai_memory",
    cosmos_container="memories",
    ai_foundry_endpoint="<foundry-endpoint>",
    embedding_deployment_name="<embedding-deployment-name>",
    chat_deployment_name="<chat-deployment-name>",
    use_default_credential=True,
)

memory.connect_cosmos(endpoint="<cosmos-endpoint>")

USER = "shopper-4471"
THREAD = "thread-001"

turns = [
    ("user", "I ride a road bike and I only want components that fit a carbon frame."),
    ("agent", "Understood. I'll keep recommendations to carbon-compatible parts."),
    ("user", "Also, my budget tops out around 900 dollars per component."),
]

for role, content in turns:
    memory.upsert_memory(user_id=USER, thread_id=THREAD, role=role, content=content)

memory.process_now(user_id=USER, thread_id=THREAD)
print("Turns stored and processed.")
```

Run it:

```bash
python shopper_memory.py
```

`connect_cosmos` opens the preprovisioned containers without creating resources. The constructor deliberately omits `cosmos_endpoint`: supplying it invokes `create_memory_store` automatically, which uses data-plane creation calls. `process_now` then runs the pipeline that turns those raw turns into durable memory. Fact extraction already runs on its own cadence by this point; the explicit call is what produces the thread and user summaries, which otherwise wait for much higher turn counts.

> [!NOTE]
> The role on each turn is `user` or `agent`. The toolkit accepts `user`, `agent`, `tool`, and `system`, and rejects anything else, so `assistant` fails validation.

Now recall from a different conversation. Comment out the whole `for role, content in turns:` block, including the indented line beneath it, so the same turns aren't written a second time. Then add the following code to the end of the file and run it again:

```python
hits = memory.search_cosmos(
    search_terms="frame material and budget preferences",
    user_id=USER,
    top_k=5,
    min_confidence=0.7,
)

for hit in hits:
    print(hit.get("type"), "-", hit["content"])

print("\nProfile:", memory.get_user_summary(user_id=USER))
```

The search is scoped to the user rather than the thread, so a brand-new conversation recalls everything learned earlier. What comes back is extracted facts, not the original sentences: the toolkit decided what was worth keeping. The `min_confidence` filter excludes memories with scores below 0.7. Inferred facts can still meet that threshold, and a confidence score doesn't prove that a memory is correct or explicitly stated.

## Task 4: Separate what the tools own from what you own

Go back to the assistant in Visual Studio Code and point it at what the toolkit built:

```text
List the containers in the ai_memory database, and infer the schema
of the memories container.
```

The loop closes here: the design-time tool inspecting the run-time tool's output. You should see the toolkit's containers, and memory documents carrying `type`, `content`, `confidence`, `user_id`, and `thread_id` among other properties.

Now answer three questions from what you observed, not from recall:

1. **Which container holds the raw turns, and which holds the extracted facts?** The toolkit chose that split and the partition key underneath it. Would you choose the same key for the `product` container in Task 1?
2. **Which settings did you supply before connecting?** You configured throughput and indexing when you provisioned the memory containers. The toolkit uses those resources; your team remains responsible for their capacity and indexing choices.
3. **What ran that you didn't call?** Task 3 called `process_now` once, but writing turns also triggers embedding and extraction on a turn-count cadence. Each one is a model call billed to your Foundry deployment.

The pattern arrived complete. The decisions underneath it didn't move.

## Clean up resources

When you finish the course, delete resources you no longer need. Delete the resource group only if you created it for the course and every resource in it can be removed:

```azurecli
az group delete --name $resourceGroup --yes --no-wait
```

If your lab environment provided the resource group, delete only the Azure Cosmos DB account instead:

```azurecli
az cosmosdb delete --name $accountName --resource-group $resourceGroup --yes
```

Apply the same rule to the resource group holding your Microsoft Foundry project. Keep shared and lab-provided resource groups, and remove only the lab resources you created and no longer need. Don't delete a shared Foundry account or deployments that other applications use.

The provisioned-throughput containers in this exercise incur throughput and storage charges while they exist. Serverless accounts instead charge for consumed request units and storage. Pay-per-token model deployments charge for inference usage, but provisioned model deployments incur capacity charges even while idle.
