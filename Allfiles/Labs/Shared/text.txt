In this exercise, you connect an AI assistant to the CosmicWorks product catalog through a Model Context Protocol (MCP) server. You then use the Agent Memory Toolkit to store and retrieve a shopper's preferences in Azure Cosmos DB.

## Before you start

To complete this exercise, you need an [Azure subscription](https://azure.microsoft.com/free/) with permission to create resources and assign roles.

If your lab environment isn't set up yet, follow [Set up your lab environment](https://github.com/MicrosoftLearning/dp-420-cosmos-db-dev/blob/main/Allfiles/Labs/Shared/00-setup-local-environment.md) to install Visual Studio Code, Git, the Azure CLI, and PowerShell 7.

You also need [Python](https://www.python.org/downloads/) 3.12 or 3.13 installed.

This exercise also requires:

- Quota for `text-embedding-3-small` and `gpt-5.4-mini` in the Foundry region. Setup creates the Foundry resource, project, and model deployments.
- [Node.js](https://nodejs.org) 22 or later, which supplies the `npx` command the MCP server runs under.
- Visual Studio Code with the [GitHub Copilot](https://marketplace.visualstudio.com/items?itemName=GitHub.copilot) extension.

## Set up your Azure Cosmos DB resources

This exercise uses the `aitools` profile, which creates the CosmicWorks catalog and the Agent Memory Toolkit's containers. It enables vector search, so use a disposable account rather than the shared core account. You don't need an existing Foundry project.

Setup runs in two stages. The first creates the Cosmos DB account and Foundry model deployments. After you confirm Cosmos DB search-feature enrollment in the portal, the second creates the databases, containers, and Cosmos DB role assignment.

1. Start **Visual Studio Code**.

1. If you don't have the lab code yet, clone the repository for DP-420: open the command palette with Ctrl+Shift+P, run Git: Clone, and enter the following URL. Choose a local folder when prompted. Otherwise, open the folder from your previous clone.

    ```
    https://github.com/microsoftlearning/dp-420-cosmos-db-dev
    ```

1. Once the repository is cloned, open that local folder in **Visual Studio Code**.

1. In the **Explorer** pane, browse to the **Allfiles/Labs/Shared** folder.

1. Open the context menu for the folder and select **Open in Integrated Terminal**. If the terminal isn't PowerShell, select the dropdown beside the **+** in the terminal toolbar and choose **PowerShell**.

1. Sign in to the Azure CLI. A browser window opens so you can sign in to Azure.

    ```azurecli
    az login
    ```

1. Set variables for the resource group and regions. If your lab environment provides a resource group, use that name. Otherwise, use a new group that contains only this exercise's resources. Foundry can use a different region from Cosmos DB.

    ```powershell
    $resourceGroup = "dp420-ai-tools"
    $location = "westus2"
    $foundryLocation = "eastus"
    ```

1. Run the setup script.

    ```powershell
    ./setup.ps1 -ResourceGroup $resourceGroup -Location $location -NamePrefix dp420lab08 -LabProfile aitools -AccountOnly -EnableFoundry -FoundryLocation $foundryLocation
    ```

    Azure Cosmos DB account names have to be globally unique, so the script builds one for you by adding six random characters to the prefix, giving a name like `dp420lab08a7f3k9`.

1. Wait for the account and model deployments to finish. Deployment time varies by region and available capacity.

1. Record the **Account name**, **Account endpoint**, **Foundry account**, and **OpenAI endpoint** values the script prints. The Cosmos DB endpoint looks like `https://<your-account-name>.documents.azure.com:443/`. Setup also saves the Foundry settings in `logs/foundry-<account-name>.json`.

1. Set a variable for the account name so the Azure CLI commands in this exercise can use it.

    ```powershell
    $accountName = "<your-account-name>"
    ```

1. Open that Cosmos DB account in the Azure portal. Under **Settings**, select **Features**. Confirm **Vector Search for NoSQL API** is enabled, then enable **Full Text & Hybrid Search for NoSQL API**. Allow up to 15 minutes for enrollment and confirm both features are enabled before continuing.

1. Resume setup against the same account, then verify the resources. The confirmation switch records your portal check; it doesn't enable or independently verify feature enrollment.

    ```powershell
    ./setup.ps1 -ResourceGroup $resourceGroup -Location $location -AccountName $accountName -LabProfile aitools -SearchFeaturesReady -EnableFoundry -FoundryLocation $foundryLocation
    ./verify.ps1 -ResourceGroup $resourceGroup -AccountName $accountName -LabProfile aitools -EnableFoundry
    ```

    Continue only after both commands succeed. If Foundry deployment fails because of model availability or quota, resolve the issue and retry against this Cosmos DB account. Keep any `-FoundryLocation` or `-FoundryAccountName` overrides consistent on both setup stages.

1. Load the saved model settings in the **Allfiles/Labs/Shared** terminal.

    ```powershell
    $foundry = Get-Content "./logs/foundry-$accountName.json" -Raw | ConvertFrom-Json
    $openAiName = $foundry.FoundryAccountName
    $foundry | Format-List FoundryAccountName, OpenAiEndpoint, EmbeddingDeployment, EmbeddingDimensions, ChatDeployment
    ```

After both stages, setup creates these resources:

| Resource | Configuration |
| :--- | :--- |
| Azure Cosmos DB account | API for NoSQL, key-based authentication disabled, vector search enabled |
| `cosmicworks` database | Holds the catalog and the core profile's supporting containers |
| `cosmicworks/product` | `/categoryId`, autoscale maximum of 1,000 request units per second, 295 products |
| `cosmicworks/productMeta` | `/type`, autoscale maximum of 1,000 request units per second, 237 category and tag documents |
| `cosmicworks/leases` | `/id`, 400 request units per second, empty |
| `cosmicworks/operations` and `cosmicworks/bulkload` | `/categoryId`, each with an autoscale maximum of 1,000 request units per second, empty |
| `ai_memory` database | Holds the five Agent Memory Toolkit containers |
| `ai_memory/memories` | Hierarchical `/user_id`, `/thread_id` key, autoscale maximum of 1,000 request units per second, TTL enabled without default expiry |
| `ai_memory/memories_turns` | Same key and throughput, 30-day default TTL |
| `ai_memory/memories_summaries` | Same key and throughput, TTL enabled without default expiry, summary composite index |
| `ai_memory/counter` | Hierarchical `/user_id`, `/thread_id` key, autoscale maximum of 1,000 request units per second |
| `ai_memory/leases` | `/id`, autoscale maximum of 1,000 request units per second |
| Cosmos DB role assignment | Cosmos DB Built-in Data Contributor, granted to your signed-in identity |
| Microsoft Foundry resource and project | Key-based authentication disabled; project named `dp420` |
| Model deployments | `text-embedding-3-small` version `1` on Standard and `gpt-5.4-mini` version `2026-03-17` on GlobalStandard, each with 30 capacity units |
| Foundry role assignment | Foundry User, granted to your signed-in identity on the Foundry resource |

The three memory data containers use a full-text policy and index on `/content` and a `quantizedFlat` vector index on `/embedding`, with 1,536 dimensions and cosine distance. The embedding model produces that vector length. Time to live (TTL) removes expired turns; the other memory records have no default expiry.

Because key-based authentication is disabled, no key or connection string appears anywhere in this exercise. Every operation authenticates with the identity from your `az login` session, which is the recommended approach for new accounts.

> [!NOTE]
> A new role assignment takes a few minutes to propagate. If a later step fails with a 403 error, wait a moment and try again.

## Task 1: Set up the project and confirm the catalog

The setup script grants **Cosmos DB Built-in Data Contributor**, which allows writes. The MCP server you configure next only reads, so in a production deployment it would take **Cosmos DB Built-in Data Reader** instead.

Create a project folder and set up a virtual environment:

```bash
mkdir ai-tools-lab
cd ai-tools-lab
python -m venv .venv
```

Activate the environment. On Windows:

```powershell
.venv\Scripts\activate
```

On macOS or Linux:

```bash
source .venv/bin/activate
```

Install the packages:

```bash
pip install azure-cosmos azure-identity
```

Confirm the catalog loaded. In the **ai-tools-lab** folder, alongside the **.venv** folder rather than inside it, save the following code as `check_catalog.py`, replacing the endpoint:

```python
from azure.cosmos import CosmosClient
from azure.identity import DefaultAzureCredential

ENDPOINT = "<cosmos-endpoint>"

client = CosmosClient(ENDPOINT, credential=DefaultAzureCredential())
container = client.get_database_client("cosmicworks").get_container_client("product")

count = list(container.query_items(query="SELECT VALUE COUNT(1) FROM c"))[0]

print(f"Catalog holds {count} products")
```

Run it:

```bash
python check_catalog.py
```

The output reports 295 products.

## Task 2: Connect an AI assistant with the Azure MCP Server

Create a `.vscode` folder in the project, and add a file named `mcp.json`:

```json
{
  "servers": {
    "Azure MCP Server": {
      "command": "npx",
      "args": ["-y", "@azure/mcp@latest", "server", "start"]
    }
  }
}
```

Open the folder in Visual Studio Code, open GitHub Copilot, and switch to **Agent** mode. Refresh the tools list and confirm the Azure MCP Server appears. The server authenticates with the credentials your `az login` already established, so nothing else needs configuring.

Now work the catalog through the assistant. Start with the question you'd otherwise answer by opening documents by hand:

```text
Infer the schema of the product container in the cosmicworks database
for my Azure Cosmos DB account.
```

The assistant reports the top-level properties and how many sampled documents carried each one. Compare those properties against the shape you know from earlier in this learning path: `id`, `categoryId`, `categoryName`, `sku`, `name`, `description`, `price`, and `tags`.

Ask for recent writes, which is how you'd confirm a load succeeded without writing a query:

```text
Show me the 5 most recently modified items in the product container.
```

Then ask a real question about the data:

```text
Query the product container for items where categoryId is
3E4CEACD-D007-46EB-82D7-31F6141752B2, and return only name and price.
```

Approve each tool call when prompted. Notice what the assistant reports back: the tool it chose, and the results it got.

> [!NOTE]
> The server also carries text search and vector similarity search. Neither is exercised here, because text search needs a full-text index on the target property and vector search needs both a vector index and an embedding deployment. The `product` container has neither. That constraint belongs to the tools, not to your prompt: they operate on the indexing policy you configured.

Before moving on, note what didn't happen. You asked the assistant about your data several times and it never offered to change it. Every Azure Cosmos DB tool in the server is read-only.

## Task 3: Add durable memory with the Agent Memory Toolkit

The assistant helped you understand the catalog. It did nothing for the application, which still forgets a shopper between messages.

Setup grants the **Foundry User** role separately from the Cosmos DB data-plane role. Both are required: the application stores memory in Cosmos DB and calls the Foundry models to extract and embed it.

Install the memory toolkit:

```bash
pip install azure-cosmos-agent-memory==0.3.0b2
```

> [!IMPORTANT]
> Pin the version. This package is in preview, its public surface is still changing between releases, and the toolkit's own guidance is to pin when integrating.

The `aitools` profile provisions the database and containers through Azure Resource Manager. The application only connects to them. Microsoft Entra ID doesn't authorize database or container creation through the Cosmos DB data-plane SDK, so don't move that setup into the application.

Save the following code as `shopper_memory.py`. Replace `<foundry-endpoint>` with **OpenAiEndpoint** from the saved settings, and replace `<cosmos-endpoint>` with the Cosmos DB account endpoint. The model deployment names match the setup defaults.

```python
from azure.cosmos.agent_memory import CosmosMemoryClient

memory = CosmosMemoryClient(
    cosmos_database="ai_memory",
    cosmos_container="memories",
    ai_foundry_endpoint="<foundry-endpoint>",
    embedding_deployment_name="text-embedding-3-small",
    embedding_dimensions=1536,
    chat_deployment_name="gpt-5.4-mini",
    use_default_credential=True,
)

memory.connect_cosmos(endpoint="<cosmos-endpoint>")

USER = "shopper-4471"
THREAD = "thread-001"

turns = [
    ("user", "I ride a road bike and I only want components that fit a carbon frame."),
    ("agent", "Understood. I'll keep recommendations to carbon-compatible parts."),
    ("user", "Also, my budget tops out around 900 dollars per component."),
]

for role, content in turns:
    memory.upsert_memory(user_id=USER, thread_id=THREAD, role=role, content=content)

memory.process_now(user_id=USER, thread_id=THREAD)
print("Turns stored and processed.")
```

Run it:

```bash
python shopper_memory.py
```

`connect_cosmos` opens the preprovisioned containers without creating resources. The constructor deliberately omits `cosmos_endpoint`: supplying it invokes `create_memory_store` automatically, which uses data-plane creation calls. `process_now` then runs the pipeline that turns those raw turns into durable memory. Fact extraction already runs on its own cadence by this point; the explicit call is what produces the thread and user summaries, which otherwise wait for much higher turn counts.

> [!NOTE]
> The role on each turn is `user` or `agent`. The toolkit accepts `user`, `agent`, `tool`, and `system`, and rejects anything else, so `assistant` fails validation.

Now recall from a different conversation. Comment out the whole `for role, content in turns:` block, including the indented line beneath it, so the same turns aren't written a second time. Then add the following code to the end of the file and run it again:

```python
hits = memory.search_cosmos(
    search_terms="frame material and budget preferences",
    user_id=USER,
    top_k=5,
    min_confidence=0.7,
)

for hit in hits:
    print(hit.get("type"), "-", hit["content"])

print("\nProfile:", memory.get_user_summary(user_id=USER))
```

The search is scoped to the user rather than the thread, so a brand-new conversation recalls everything learned earlier. What comes back is extracted facts, not the original sentences: the toolkit decided what was worth keeping. The `min_confidence` filter excludes memories with scores below 0.7. Inferred facts can still meet that threshold, and a confidence score doesn't prove that a memory is correct or explicitly stated.

## Task 4: Separate what the tools own from what you own

Go back to the assistant in Visual Studio Code and inspect what the toolkit stored:

```text
List the containers in the ai_memory database, and infer the schema
of the memories container.
```

The loop closes here: the design-time tool inspecting the run-time tool's output. You should see the toolkit's containers, and memory documents carrying `type`, `content`, `confidence`, `user_id`, and `thread_id` among other properties.

Now answer three questions from what you observed, not from recall:

1. **Which container holds the raw turns, and which holds the extracted facts?** The toolkit chose that split and the partition key underneath it. Would you choose the same key for the `product` container in Task 1?
2. **Which settings did setup supply before connecting?** The setup profile configured throughput and indexing for the memory containers. The toolkit uses those resources; your team remains responsible for their capacity and indexing choices.
3. **What ran that you didn't call?** Task 3 called `process_now` once, but writing turns also triggers embedding and extraction on a turn-count cadence. Each one is a model call billed to your Foundry deployment.

The pattern arrived complete. The decisions underneath it didn't move.

## Clean up resources

When you finish this exercise, delete its resources if you no longer need them. Delete the resource group only if you created it for this exercise and every resource in it can be removed:

```azurecli
az group delete --name $resourceGroup --yes --no-wait
```

If your lab environment provided the resource group, keep it. Delete only the Cosmos DB and Foundry resources you created for this exercise, after confirming that no other application uses them:

```azurecli
az cosmosdb delete --name $accountName --resource-group $resourceGroup --yes
az cognitiveservices account delete --name $openAiName --resource-group $resourceGroup
```

Keep shared and lab-provided resource groups. Don't delete a reused Foundry account or deployments that other applications use.

The provisioned-throughput containers in this exercise incur throughput and storage charges while they exist. Serverless accounts instead charge for consumed request units and storage. Pay-per-token model deployments charge for inference usage, but provisioned model deployments incur capacity charges even while idle.
